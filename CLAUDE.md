# Puppy tracker

A shared care and training log for a new puppy. Family members each use the app on their own phone and see each other's entries in real time. It is also a portfolio project, so the quality of the infrastructure matters as much as the features.

## About the developer

- Linux sysadmin: comfortable with the shell, Docker, CI and infrastructure.
- Newer to front-end development. Explain React, TypeScript and web concepts in plain language, and work in small steps rather than making large changes at once.
- Wants the infra side deliberately well engineered (IaC, CI/CD, TLS, backups, monitoring) to keep skills current and to show off. Likes Go; a Go backend embedding PocketBase is a "later" idea.
- Develops on Windows 11 with WSL2 (Ubuntu), VS Code and bash.

## Stack

- `app/`: Vite + React + TypeScript phone app (PWA planned), using the PocketBase JS SDK. Linted with oxlint.
- `backend/`: PocketBase in Docker. The Dockerfile downloads the release given by the `PB_VERSION` build arg, which is pinned in `compose.yaml`. Migrations live in `backend/pb_migrations/`, are generated by the PocketBase dashboard, and must be committed. That directory is bind-mounted into the container, so a dashboard change writes a new migration file straight into the repo.
- `compose.yaml`: local environment. `scripts/smoke-test.sh`: API smoke test. `.github/workflows/ci.yml`: CI. `docs/`: data model, workflow guide, and ADRs in `docs/adr/`.
- The Vite dev server proxies `/api` to PocketBase on port 8090, so the app makes same-origin requests (`new PocketBase('/')`).

## Commands

- Backend: `docker compose up -d --build`. Admin UI at http://localhost:8090/_/
- App, from `app/`: `npm run dev -- --host` (port 5173, strict), `npm run lint`, `npm run build`
- Smoke test: `PB_SUPERUSER_EMAIL=<superuser email> ./scripts/smoke-test.sh` (prompts for the password)
- Before finishing a change, run lint, build, and the smoke test if the backend or data model changed.
- There is no unit test runner. `npm run build` runs `tsc -b`, so it is also the type check. The smoke test (bash, curl, jq) is the only automated test. It creates throwaway users and a dog, checks the API rules end to end, then cleans up. CI (`ci.yml`) runs lint and build, then starts the backend, creates a throwaway superuser and runs the smoke test.

## How the app fits together

- `App.tsx` shows `Login` or `Home` depending on `pb.authStore`. `Home.tsx` holds almost all the state. It loads the first dog and the latest 200 events, and it subscribes to realtime changes on `events`, reloading the whole list on any change. The "time since" tiles at the top of `Home.tsx` are hardcoded matchers on `type` and `data`. `EditSheet.tsx` edits and deletes an entry.
- An `EventDef` (`events/types.ts`) is `type`, `label`, `toggles` (yes/no keys stored in `data`; no toggles means one tap logs it) and `summary(data)`. The log buttons, the toggle picker and the edit sheet are all driven by `registry.ts`. `defFor()` returns a generic fallback for unknown types. A new type that should have a "time since" tile also needs an entry in `tiles` in `Home.tsx`.
- New events get their id from `newId()` on the client, so retries never create duplicates. The server rejects a repeated id.
- API rules (set through migrations): only signed-in users can read or write `dogs` and `events`, and creating an event requires `logged_by` to be the signed-in user. If you change a rule, update `scripts/smoke-test.sh` to match.

## Data model rules (see docs/data-model.md)

- One `events` collection: `id` (15 characters, generated on the client), `dog`, `type`, `started_at`, `ended_at` (optional), `logged_by`, `note`, `data` (JSON), `v`.
- **Add, never change.** New optional fields, new event types and new collections are fine. Never rename, remove or repurpose a field.
- Readers must tolerate missing fields, `null`, and `""` (PocketBase returns `""` for empty optional fields), and unknown event types.
- Each event type is one module in `app/src/events/`, registered in `registry.ts`. Adding a type means adding a module.
- Times are stored in UTC. PocketBase dates use a space instead of a `T`, so parse them with `toDate()` from `app/src/lib/time.ts` (Safari can't parse the raw format).
- Schema changes go through PocketBase migrations.

## Conventions

- TypeScript strict. Keep components small. Plain CSS using the design tokens at the top of `src/index.css`.
- UI copy: sentence case and active voice. Errors say what went wrong and what to do next.
- Mobile first: large tap targets. It must work on a phone over plain HTTP on the home network.
- Conventional commits: `feat(app): ...`, `fix(app): ...`, `ci: ...`, `docs: ...`.

## Workflow

- Work is tracked in GitHub Issues and a Projects board. See `docs/workflow.md`.
- One branch per issue (`feat/12-short-name`), a pull request containing `Closes #12`, CI green, squash merge.
- Never commit secrets, `.env` files or `pb_data/`.

## Current decisions and constraints

- Phone access is plain HTTP over home Wi-Fi, served from the laptop (WSL mirrored networking). HTTPS, which is needed for PWA install and offline mode, is a planned decision to be recorded as an ADR.
- Offline queue, the words library, insights and production infrastructure are on the backlog as GitHub milestones.
