# ADR 0004: Reach prod through Tailscale Serve and Caddy

Status: accepted
Date: 2026-10-12

## Context

ADR 0002 chose Caddy as the reverse proxy and Tailscale Serve for HTTPS. ADR 0003 put production on a VM inside WSL2 and left open how the two fit together there.

The VM sits behind libvirt's NAT inside WSL, so a phone cannot reach it directly. Whatever reaches it must cross that boundary, and it must give a valid HTTPS certificate, because the PWA and its service worker need one.

Constraints:

- Phones keep working through host changes. The installed PWA is tied to its hostname, so the hostname must survive a move to another machine, or to AWS and back (ADR 0002).
- Nothing is exposed to the home network or the internet.
- The same setup must work on the new PC, the Pi or a cloud host.
- Spend stays at about zero.

## Decision

1. **Tailscale runs on the prod VM itself.** An Ansible role installs it. The VM joins the tailnet with outbound connections only, so the NAT does not matter.
2. **Tailscale Serve terminates HTTPS** on port 443, using a certificate Tailscale issues for the node's `ts.net` name, and forwards to Caddy on `127.0.0.1:8080`.
3. **Caddy runs in Docker** from a new `compose.prod.yaml`, together with the PocketBase backend. Both images come from GHCR (#80). Only Caddy is published, and only on `127.0.0.1:8080`. The backend is reachable only from the compose network. Caddy serves the built app and proxies `/api/*` to the backend, with response buffering off so PocketBase's realtime connections work.
4. **The node is named `puppy`,** not `puppy-prod` and not the machine's name. The URL is `https://puppy.<tailnet>.ts.net`. The name belongs to the node, so a replacement host takes it over: remove the old node, join the new machine as `puppy`. Phones then see the same hostname and keep their installed app. Prod and scratch use different node names.
5. **The existing tailnet is kept.** Dev already runs on it, as the laptop's own node, and phones already use that address. Its name was generated by Tailscale and can be changed in the admin console, but renaming it changes every address on it, dev included, so it is left alone. Prod joins as a second node. Dev and prod are different hostnames, so a phone that installed the PWA from dev installs it again from prod once, at the first release (ADR 0003, decision 9). After that the prod address does not change.
6. **The firewall stays closed to the network.** Only SSH is open, with its existing rate limit. No rule is added for the tailnet: Tailscale Serve is handled inside `tailscaled`, and it was confirmed on the scratch VM that the app is reachable over the tailnet with only SSH allowed. Anything else on the VM, including ports published by Docker apart from the loopback one, stays unreachable from the tailnet too.
7. **The PocketBase admin UI (`/_/`) stays reachable to anyone on the tailnet,** as accepted in ADR 0002. Only family are on it. This is revisited if anyone else joins.
8. **The first join is manual.** `tailscale up --hostname=puppy` is run once on the VM. Automating it needs an auth key, which is a secret, so that waits for encrypted secrets (#25).
9. **Everything is tried on the scratch VM first,** joined as a throwaway node, then repeated on prod.
10. **A custom domain is not bought now.** It would remove the dependence on Tailscale for the hostname, and it costs about $10–15 a year plus Caddy fetching its own certificates by DNS challenge. Revisit it if Tailscale's terms change or the app goes public.

## Consequences

Good:

- No ports are open on any network. The tailnet is the only way in.
- Certificates renew themselves, with nothing to open or configure at the edge.
- The same role and compose file work on any host that can run Tailscale, which keeps the AWS migration exercise in ADR 0002 simple.
- The URL stays the same through host moves, as long as the node name is reused.

Costs:

- **Tailscale is in the path.** If its free plan or terms change, the URL and access change with it. A custom domain (decision 10) is the way out.
- **One admin setting to check:** HTTPS certificates must be enabled for the tailnet (DNS settings in the Tailscale admin console). Dev already uses a certificate, so it is probably on.
- **Phones reinstall the app once** at the first release, because prod has a different hostname from dev.
- **Caddy's own TLS goes unused.** It stays because it gives the single-page app its `index.html` fallback, compression, headers and the `/api` proxy, which Tailscale Serve does not do.
- **Every family phone needs the Tailscale app** and access to the tailnet, as in ADR 0002.
- **Moving the node name needs care.** The old node must be removed before the new one joins, or the new one gets a suffixed name such as `puppy-1`.
- **The certificate is reissued** when a new machine takes over the name.

## Alternatives considered

- **Caddy terminates TLS itself, using the Tailscale certificate (A2).** Works, and uses more of Caddy. It needs Caddy to be allowed to use Tailscale's certificates and to listen on the tailnet interface, which is more to set up and to move between hosts. Kept as a later option.
- **Tailscale on the Windows host, forwarding to the VM.** This is how dev works. The Windows host cannot route to a VM inside WSL's NAT, so it needs fragile port forwarding that would not carry over to a real home server.
- **A Tailscale subnet router advertising the VM network.** Phones would reach the VM by IP address with no `ts.net` name, so no valid certificate, and the PWA would not install.
- **Caddy's internal certificate authority.** Every phone would have to trust a custom root certificate. Fine for testing on scratch, not for the family.
- **A Cloudflare Tunnel with a domain.** Costs a domain each year and puts a third party in front of the app. Still the later option in ADR 0002.
- **Traefik instead of Caddy.** ADR 0002 already chose Caddy, and the app image already uses it.
